## 2. TriggerDecision → CyberHeal Mapping

The `PredictiveIncidentAdapter` maps the frozen Phase 2 `TriggerDecision` into CyberHeal data contracts:

| Phase 2 TriggerDecision Attribute | Phase 3 CyberHeal Mapping (`AgentState` / `HumanReviewPayload`) | Purpose |
| :--- | :--- | :--- |
| `decision` | `status` (`AUTO_TRIGGERED` / `ESCALATED_HUMAN_REVIEW` / `SUPPRESSED`) | Gating outcome controlling execution. |
| `risk_score` | `trajectory_risk_score` (`float`), `alert_payload["risk_score"]` | Predictive anomaly magnitude for Sentinel and Guardian. |
| `confidence` | `confidence_score` (`float`), `alert_payload["confidence"]` | Informs Causor RCA and Guardian approval threshold ($\ge 0.70$). |
| `evidence_strength` | `evidence_strength` (`float`), `alert_payload["evidence_strength"]` | Supporting telemetry density indicator. |
| `predicted_stage` | `attack_stage` (`str`), `alert_payload["predicted_stage"]` | Defense-aligned MITRE stage for dynamic RCA diagnosis. |
| `asset_criticality` | `asset_criticality` (`str`), `alert_payload["asset_criticality"]` | Protects sensitive assets from unsafe automation. |
| `action_safety` | `action_safety` (`str`), `alert_payload["action_safety"]` | Ensures blast radius containment. |
| `reasons` | `predictive_reasons` (`list[str]`), `alert_payload["reasons"]` | Human-readable explanation of why trigger occurred. |
| `blocking_reasons` | `predictive_blocking_reasons` (`list[str]`) | Explains why automated execution was withheld. |
| `risk_trajectory_summary` | `risk_trajectory` (`dict | None`) | Multi-horizon escalation context ($k \in \{1, 3, 5\}$). |
| `to_dict()` | `trigger_decision` (`dict[str, Any]`) | Full immutable audit record preserved in `AgentState`. |

## 3. AUTO_TRIGGER Path

When `decision == AUTO_TRIGGER`:
1. `PredictiveIncidentAdapter` validates all fields and constructs an `AgentState` with:
   - `incident_type = "PREDICTIVE"`
   - `status = "OPEN"`
   - `alert_payload["source"] = "TRINETRA_PREDICTIVE"`
   - `alert_payload["trigger_type"] = "PREDICTIVE"`
2. The predictive event enters `IntakeAgent` $\to$ `SentinelAgent` $\to$ `ThreatIntelAgent` $\to$ `CausorAgent`.
3. `SentinelAgent` creates a predictive anomaly record `ANOM-PRED-*` tracking `forecasted_network_drift` and `top_predictive_features`.
4. `CausorAgent` integrates the predictive attack stage and confidence score into the localized root cause.
5. The plan is generated by `PlannerAgent` and forwarded to **`GuardianAgent`**.
6. **Crucial Rule:** AUTO_TRIGGER certifies the event as **eligible for CyberHeal intake**, NOT direct remediation. `GuardianAgent` retains full safety veto authority.

---

## 4. HUMAN_REVIEW Path

When `decision == HUMAN_REVIEW`:
1. `PredictiveIncidentAdapter` creates an immutable `HumanReviewPayload` containing the entire threat profile, top feature drivers, reasons, and blocking reasons.
2. The adapter returns `PredictiveHandoffStatus.ESCALATED_HUMAN_REVIEW`.
3. **No automated remediation is initiated.** No `AgentState` is passed to the execution pipeline.
4. The event is queued for human SOC analyst inspection via the escalation boundary.

---

## 5. NO_TRIGGER Path

When `decision == NO_TRIGGER`:
1. `PredictiveIncidentAdapter` suppresses the event.
2. Returns `PredictiveHandoffStatus.SUPPRESSED` with `agent_state = None`.
3. Zero remediation incidents or tickets are created, preventing operator alert fatigue.

---

## 6. Guardian Safety Boundary Preservation

TRINETRA's Trigger Gate and CyberHeal's Guardian serve distinct, non-overlapping safety roles:
- **TRINETRA Trigger Gate:** Evaluates *"Is the predictive forecast reliable and safe enough to notify CyberHeal?"*
- **CyberHeal Guardian:** Evaluates *"Is the proposed remediation action safe to execute on the live infrastructure?"*

Guardian checks remain 100% active:
- If `state.confidence_score < 0.70`, Guardian **rejects** the remediation plan (`guardian_approved = False`), triggering `ReflectiveLearningAgent` (RLM).
- If `state.confidence_score >= 0.70`, Guardian approves the plan (`guardian_approved = True`).
- Under no circumstance does TRINETRA bypass Guardian.

---

## 7. Diagnosis & Root Cause Analysis (RCA) Integration

`CausorAgent` incorporates TRINETRA predictive context:
- Description is enriched: `"Forecasted {attack_stage} attack with predictive risk {trajectory_risk_score:.2f}."`
- Confidence score is anchored by model confidence, ensuring RCA reflects forecast reliability.
- Top contributing network features (e.g. `macro_mean_byte_rate`, `flags_syn_count`) are preserved in `anomalies` for downstream inspection.

---

## 8. Planner Boundary

TRINETRA never generates raw shell scripts or firewall commands.  
`PlannerAgent` remains exclusively responsible for translating the identified root cause into a constrained remediation plan (e.g. `[{"action": "block_ip", "target": target_ip, "status": "PENDING"}]`).

---

## 9. Executor Boundary & Safe Demo Mode

TRINETRA modules contain **zero** execution logic (`subprocess.run`, `netsh`, or `iptables`).  
In `ExecutorAgent`:
- `CYBERHEAL_SAFE_MODE` defaults to `True`.
- In safe simulation mode, firewall actions are simulated (`simulated_blocked`), protecting the host operating system from destructive network disruptions during testing and offline demonstrations.

---

## 10. Verification Boundary

`VerifierAgent` receives the normal CyberHeal execution context. Because `AgentState` carries the predictive metadata through the pipeline, verification can correlate the original forecast with the post-remediation system state.

---

## 11. RLM Metadata Preservation

`ReflectiveLearningAgent` (RLM) history and retry counts are preserved. The complete `trigger_decision` dictionary remains accessible in `AgentState`, enabling future Phase 5 learning loops to assess forecast accuracy against remediation success.

---

## 12. Traceability & Auditability

Every predictive event is assigned:
- `incident_id`: e.g. `INC-PRED-999`
- `trace_id`: e.g. `TRACE-INC-PRED-999`
- `blockchain_sys`: ScribeAgent commits the resolution event hash to `blockchain.json` upon completion, preserving tamper-proof audit trails.

---

## 13. Failure Handling

If input data is malformed (e.g., missing fields, non-finite floats, invalid strings):
- `PredictiveIncidentAdapter` fails safely to `PredictiveHandoffStatus.REJECTED_INVALID`.
- An error trace ID is emitted with descriptive diagnostic reasons.
- Never defaults to `AUTO_TRIGGER` or remediation execution on failure.

---

## 14. Backward Compatibility

- Existing reactive alerts continue to use `AgentState(incident_id=..., alert_payload=...)` with default `incident_type = "REACTIVE"`.
- All legacy reactive agent pathways execute identically to their Phase 0 baseline.
- All 62 baseline tests and 56 Phase 1-2 tests continue to pass with 0 regressions.

---

## 15. Offline Operation

The integration adapter is implemented in pure Python and NumPy with zero network, cloud, or external database dependencies.

---

## 16. Limitations

1. **Simulated Verification:** `VerifierAgent` currently uses attempt-based resolution simulation rather than live packet replay delta verification (addressed in Phase 4).
2. **Static Target IP:** When telemetry does not specify an attacking IP, the adapter defaults to a configured fallback IP (`192.168.1.100`).
